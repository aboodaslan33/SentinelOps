## 2. Description

At 15:30:07 UTC an elevated session on `WIN-SOC-EP01` performed three privilege-related
actions within 55 seconds:

1. added the local account `lab-svc-update` to the **Administrators** group (Event 4732);
2. created a **scheduled task configured to run as `NT AUTHORITY\SYSTEM`** (Event 4698 and
   `schtasks.exe /create /ru SYSTEM`);
3. started an elevated process, producing a privileged logon with `SeDebugPrivilege` and
   `SeBackupPrivilege` assigned (Event 4672).

Each action is individually a legitimate administrative operation. **Together, in under a
minute, they are the signature of an attacker converting administrative access into durable
SYSTEM-level control** — the outcome that matters, regardless of the technique used to obtain
the initial privilege.

A fourth alert fired at 15:31:20 when the Sysmon service configuration was changed
(rule `100152`), which in a real incident would be treated as an attempt to blind the sensor.

## 5. Investigation

**Q1 — Which privilege actually changed, and for whom?**
Event 4732: `TargetUserName` = `Administrators` (the **group**), `MemberName` =
`lab-svc-update` (the **account added**), `SubjectUserName` = `lab-admin` (the **actor**).
Getting these three fields the right way round is the whole investigation — 4732 puts the
group, not the member, in `TargetUserName`.

**Q2 — Was the actor already privileged?**
Yes. 4672 at 15:29:58 shows administrative privileges assigned to logon `0x4F1C3`, and the
processes ran at **High** integrity. So this was privilege **abuse and consolidation** by an
already-administrative session, not an exploit-based elevation. In a real incident the next
question is immediately *how did that session become administrative?*

**Q3 — How did the actor get onto the host?**

```
data.win.eventdata.logonId:"0x4F1C3" AND data.win.system.eventID:4624
```

Logon **type 2 (interactive/console)**. Unlike INC-2026-003, this was not a remote session —
which in a real environment narrows the investigation to physical access or a hijacked local
session and changes the response entirely.

**Q4 — What will the scheduled task actually do?**
The 4698 event includes the task XML. Extracted and read:

```xml
<Principals><Principal id="Author">
  <UserId>S-1-5-18</UserId>          <!-- NT AUTHORITY\SYSTEM -->
  <RunLevel>HighestAvailable</RunLevel>
</Principal></Principals>
<Triggers><BootTrigger/></Triggers>
<Actions><Exec><Command>cmd.exe</Command><Arguments>/c echo lab</Arguments></Exec></Actions>
```

Key facts: **runs as SYSTEM**, **triggers at boot** (survives reboot), action is benign in this
exercise. A real attacker would place a payload path here — and the detection would be
identical, which is the point.

Confirmed on the host:

```powershell
Get-ScheduledTask -TaskName "LabUpdateCheck" | Select-Object TaskName, State, Author
(Get-ScheduledTask -TaskName "LabUpdateCheck").Principal.UserId    # S-1-5-18
```

**Q5 — Was the escalated account used?**

```
data.win.eventdata.targetUserName:"lab-svc-update" AND data.win.system.eventID:4624
```

No logons. The privilege was established but not exercised.

**Q6 — Was the sensor tampered with?**
Sysmon EID 16 (configuration change) fired at 15:31:20. In this lab it was the test script
reapplying the config; in a real incident a Sysmon config change immediately after a privilege
escalation would be treated as an attempt to disable monitoring and would escalate severity
to Critical.

**Q7 — Any credential access afterwards?**
Checked rule `100153` (LSASS handle access), Sysmon EID 10 and EID 8 (CreateRemoteThread) for
the following 2 hours. **None.** `SeDebugPrivilege` was held but not used against LSASS.

**Q8 — Any other persistence?**
Checked services (7045), registry Run keys (EID 12/13), Startup folder, WMI subscriptions
(EID 19–21), other accounts (4720). Only the single scheduled task was found.

## 7. Findings

1. **An already-administrative session consolidated its access into two durable mechanisms** —
   a privileged account and a SYSTEM-level boot-triggered scheduled task — in 38 seconds.
2. **The scheduled task is the more serious artefact.** It runs as SYSTEM (higher than the
   administrator who created it) and triggers at boot, so it survives reboot, user logoff and
   password changes.
3. **The actor was on the console (logon type 2)**, which is a materially different threat
   picture from the remote session in INC-2026-003.
4. **`SeDebugPrivilege` was granted but not used.** Documented explicitly, because the absence
   of credential-dumping evidence is itself a finding that shapes the response.
5. **The sensor configuration changed during the incident**, which in production would be
   treated as attempted evasion and would raise severity.
6. **Layered detection worked:** the audit source (4732/4698) and the process source (Sysmon)
   independently recorded the same actions, so disabling either one would not have produced a
   blind spot.

## 9. Recommendations

| # | Recommendation | Priority | Rationale |
|---|---|---|---|
| 1 | Alert on **every** scheduled task created outside `\Microsoft\Windows\` at level 12 | High | SYSTEM-level boot persistence is too dangerous to triage at Medium |
| 2 | Treat any Sysmon service/config change (EID 4 / 16) as Critical | High | If the sensor is tampered with, every other detection is unreliable |
| 3 | Remove standing local administrator rights; use just-in-time elevation | High | Removes the privilege that made all three actions possible |
| 4 | Deploy Windows **LAPS** | High | Prevents one local admin password from working across hosts |
| 5 | Set UAC to *Always notify* and enable *"Only elevate signed and validated executables"* | Medium | Breaks several published UAC-bypass variants covered by rule `100142` |
| 6 | Add a correlation rule: privileged group change **followed by** scheduled task or service creation within 10 minutes → level 14 | Medium | This exact sequence is the consolidation pattern |
| 7 | Weekly review of non-Microsoft scheduled tasks and services | Medium | Catches persistence created while logging was unavailable |
| 8 | Enable PowerShell transcription on administrative workstations | Low | Full record of what an elevated session did |

## 10. Lessons learned

* **Privilege escalation is best detected by its *outcome*, not its technique.** The lab
  produced group membership, a SYSTEM task and an elevated logon — the same artefacts an
  exploit-based escalation would produce. Detections built on outcomes survive new techniques.
* **The 4732 field layout (`TargetUserName` = group, `MemberName` = account) is a real trap.**
  Getting it wrong produces rules that silently never fire.
* **Read the task XML, always.** The principal (`S-1-5-18`) and the trigger (`BootTrigger`) are
  what make a scheduled task an incident rather than a note.
* **Recording what did *not* happen matters.** "`SeDebugPrivilege` was held but no LSASS access
  was observed" is a finding that directly shapes the credential-reset decision.
* **Detection gap identified:** no correlation rule links privilege change to subsequent
  persistence. Raised as SO-DET-005-B (recommendation #6).

returned to baseline.**
