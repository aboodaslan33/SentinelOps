## 2. Description

Between <TIMESTAMP> and <TIMESTAMP> UTC, seven distinct Windows discovery utilities were executed on
`<HOSTNAME>` from a single `cmd.exe` session, in a sequence that maps directly onto the
standard post-exploitation orientation routine: *who am I → what is this machine → what network
am I on → which accounts exist → what is running*.

Each individual command generated a level-3 informational alert (`100130`). Rule `100131`
correlated five **distinct** discovery binaries on the same host within 60 seconds and raised a
High alert.

Two further alerts fired in the same window: a process executed from a user-writable staging
directory (`100133`), and a **renamed system binary** whose on-disk name (`svchost32.exe`) did
not match the `OriginalFileName` recorded inside the PE header (`whoami.exe`) — rule `100134`.

## 5. Investigation — determining legitimate vs suspicious

This is the core analytical question for this detection, worked in the order taught in
[`suspicious-process.md`](../detection-rules/suspicious-process.md) §6:

**1. Parent process — is the chain plausible?**
`explorer.exe → cmd.exe → <discovery tools>`. A user opened a command prompt. Plausible on its
face — an administrator troubleshooting would look identical at this level. **Not conclusive.**

**2. Image path — is this the real binary?**
Six of the seven ran from `C:\Windows\System32\` (genuine). The seventh,
`C:\Users\Public\svchost32.exe`, did **not**. `Users\Public` is user-writable and contains no
legitimate executables on a standard Windows build. **Suspicious.**

**3. Name integrity — does the binary claim to be something else?**
`OriginalFileName` = `whoami.exe` while the file on disk is named `svchost32.exe`. The PE
version resource does not change when a file is renamed, so this is **deliberate renaming**
(T1036.003) — and `svchost32.exe` is a name chosen to be mistaken for the legitimate
`svchost.exe`. **Strongly suspicious; this single field settled the verdict.**

**4. Command lines — human or automation?**
`whoami /all`, `net localgroup administrators`, `ipconfig /all`. These are the *informative*
variants, exactly what someone orienting themselves would choose. A monitoring agent would run
the same subset identically every interval.

**5. Rate and variety — the decisive pattern.**
Seven distinct binaries in 49 seconds, each ~5–8 seconds apart. Too fast and too varied for
interactive human typing with pauses to read output; too varied for a scheduled monitoring
script (which repeats the *same* commands). **Consistent with a scripted recon routine.**

**6. Timing and user context.**
Standard user, working hours, no corresponding change ticket, and the user's own 4624 session
was active — so the actions were attributable to a live session, not a background service.

**7. Baseline comparison.**
The 48-hour baseline recorded a maximum of **2** distinct discovery binaries per minute during
normal use. Seven is 3.5× the observed maximum.

**8. What happened next?**
Checked for the natural follow-on steps: network connections (Sysmon EID 3) — **none**; file
writes outside `Users\Public` (EID 11) — **none**; account creation (4720), group changes
(4732), tasks (4698), services (7045) — **none**; PowerShell (4104) — **none**.

**Conclusion:** reconnaissance was performed and a masqueraded binary was executed, but the
activity stopped at the discovery stage.

## 7. Findings

1. **A scripted host-reconnaissance sequence executed under a standard user account**, covering
   user, host, network, account and process enumeration in under a minute.
2. **A renamed system utility was executed from a user-writable directory.** The mismatch
   between `Image` and `OriginalFileName` is deliberate evasion and is only visible because
   Sysmon is deployed — native 4688 does not carry that field.
3. **The activity did not progress** beyond discovery: no network egress, no persistence, no
   privilege escalation, no credential access.
4. **Individual events were correctly de-prioritised.** Every discovery command alerted at
   level 3; only the *pattern* reached level 12. Alerting on each `whoami` would have buried
   the real signal.
5. **Baseline data made the verdict defensible.** "Seven distinct binaries vs a measured
   maximum of two" is a far stronger statement than "this looked unusual".

## 9. Recommendations

| # | Recommendation | Priority | Rationale |
|---|---|---|---|
| 1 | Deploy AppLocker/WDAC rules blocking execution from `C:\Users\Public`, `%TEMP%`, `%APPDATA%` | High | Would have blocked the masqueraded binary outright |
| 2 | Investigate the initial access vector — recon implies prior execution | High | This incident is a symptom, not the root cause |
| 3 | Extend the masquerading rule to compare hashes against known-good system binaries | Medium | Catches renamed *and* modified utilities |
| 4 | Add a rule for `net.exe`/`net1.exe` used specifically for `localgroup administrators` | Medium | High-signal, low-volume enumeration of privilege |
| 5 | Restrict `cmd.exe` and `powershell.exe` for standard users via WDAC where feasible | Medium | Removes the most common recon shell |
| 6 | Add file-integrity monitoring on `C:\Users\Public` | Low | Provides earlier warning than execution |

## 10. Lessons learned

* **Frequency plus variety is the detection.** Neither `same_field` nor `different_field` alone
  would have produced a clean alert; the combination did.
* **`OriginalFileName` is the highest-value Sysmon field most analysts forget.** It resolved
  this incident in one comparison.
* **Informational rules are not wasted rules.** Level-3 `100130` events generated no noise for
  the analyst but were the raw material for the level-12 correlation.
* **Detection gap identified:** no rule correlates *recon followed by a network connection*,
  which would distinguish orientation from active lateral movement. Raised as SO-DET-004-B.
