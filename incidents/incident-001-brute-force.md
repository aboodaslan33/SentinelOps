## 2. Description

Between 09:14:02 and 09:14:35 UTC, twelve consecutive failed network logon attempts were
recorded against the local account `svc-backup` on `WIN-SOC-EP01`. All attempts originated
from a single source address, `192.168.56.30`, used logon type 3 (network / SMB) and failed
with sub-status `0xC000006A` — *wrong password for an account that exists*.

Wazuh rule `100101` correlated the burst (8 failures from the same source IP within 120
seconds) and raised a Medium alert 2 seconds after the final attempt. No successful
authentication from that source was found in the subsequent 24 hours, so rule `100102`
(successful logon after brute force) did not fire.

The activity matches a **password-guessing attack against a named service account**. It was
produced by the authorised lab script `Invoke-LabFailedLogons.ps1`.

## 5. Investigation

**Q1 — Is the alert technically valid?**
Yes. The raw JSON of three sampled events was reviewed in *Discover*. All contained
`win.system.eventID: 4625`, `win.eventdata.targetUserName: svc-backup`,
`win.eventdata.ipAddress: 192.168.56.30`, `win.eventdata.logonType: 3`. The rule logic
(8 failures / 120 s / same source IP) matched the data exactly.

**Q2 — Is the account real, and is it privileged?**

```powershell
net user svc-backup
Get-LocalGroupMember -Group "Administrators"
```
`svc-backup` exists, is enabled, and is **not** a member of Administrators or Remote Desktop
Users. Blast radius if compromised: standard-user access to this workstation only.

**Q3 — Did any attempt succeed?** (the decisive question)

```
data.win.system.eventID:4624 AND data.win.eventdata.ipAddress:"192.168.56.30"
data.win.system.eventID:4624 AND data.win.eventdata.targetUserName:"svc-backup"
```
**No results** for the 24 hours surrounding the burst. `PasswordLastSet` on the account was
unchanged. No 4740 (lockout) either — the burst of 12 exceeded the 5-attempt lockout threshold
for a *single* account, but the attempts were spread such that the lockout window had reset;
this gap is recorded in the recommendations below.

**Q4 — Was the source doing anything else?**

```
data.win.eventdata.ipAddress:"192.168.56.30"
agent.name:"WIN-SOC-EP01" AND rule.level:>=8
```
Only the 4625 events. No RDP (type 10) attempts, no SMB share access, no process creation
correlated to a remote session.

**Q5 — Any follow-on activity on the host?**
Checked 4720 (account created), 4732 (group change), 4698 (scheduled task), 7045 (service),
4104 (PowerShell) for the period 09:00–12:00 UTC. **None found.**

**Q6 — Single account or many?**
Only `svc-backup` was targeted, so this is password **guessing** (T1110.001), not spraying
(T1110.003). Rule `100104` correctly did not fire.

## 7. Findings

1. **A password-guessing attack against `svc-backup` was detected and did not succeed.**
   No successful authentication from the source IP was found in the 24-hour review window.
2. **Detection performed as designed.** The correlation rule fired on the 8th failure,
   21 seconds after the first attempt.
3. **The account name was valid.** Sub-status `0xC000006A` (wrong password, account exists)
   rather than `0xC0000064` (unknown user) means the attacker had — or guessed — a real
   username. That is meaningful even in a failed attack.
4. **The lockout policy did not trigger.** The attempt spacing (~2.75 s) combined with the
   15-minute lockout *window* meant the 5-attempt threshold was not reached within a single
   window. A gap worth fixing.
5. **No persistence, execution or privilege change followed.** The host was in the same state
   after the incident as before it.

## 9. Recommendations

| # | Recommendation | Priority | Rationale |
|---|---|---|---|
| 1 | Tighten the lockout policy: 5 attempts within a **30-minute** window | High | The current 15-minute window let 12 spaced attempts through without a lockout |
| 2 | Add a slow-brute-force rule: 15 failures from one source in **30 minutes**, level 8 | High | The current 120 s window is evaded by a patient attacker |
| 3 | Restrict SMB (445) to authorised management hosts only | High | Removes the attack path entirely |
| 4 | Review why a service account (`svc-backup`) permits interactive/network logon | Medium | Service accounts should be constrained by *Deny logon* rights |
| 5 | Alert on the **first** 4625 for any `svc-*` account | Medium | Service accounts should never fail authentication interactively |
| 6 | Add source-IP enrichment (asset inventory lookup) to the alert | Low | Speeds up "is this IP ours?" during triage |

---

## 10. Lessons learned

* **What worked:** the correlation rule fired quickly and the `same_field` condition kept the
  alert clean and attributable to a single source.
* **What did not:** the fixed 120-second window is the detection's main weakness — a
  1-attempt-per-minute attacker would never trip it. Recommendation #2 addresses this.
* **Process note:** the 7-minute gap between alert and triage was manual dashboard checking.
  In a real SOC this would be an alerting integration, not a human refreshing a page.
* **Detection improvement raised:** SO-DET-001-B (slow brute force) added to the backlog.

**Final status: CLOSED — True Positive (authorised laboratory simulation), contained, no
compromise.**
