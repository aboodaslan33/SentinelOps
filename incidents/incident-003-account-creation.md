## 2. Description

At <TIMESTAMP> UTC a new local account, `lab-svc-update`, was created on `<HOSTNAME>`. The
account was enabled and given a password in the same second, and **38 seconds later** it was
added to the local **Administrators** group.

Wazuh raised three escalating alerts: `100120` (Medium — account created), `100140` (High —
privileged group change) and `100121` (High, level 13 — the *correlation* between creation and
promotion inside the 5-minute window).

The account name was chosen to blend in with legitimate service accounts (`lab-svc-update`
reads like an update service). This is a textbook **backdoor administrator account**: durable
across reboots, invisible to antivirus, and created entirely with signed Windows binaries.

## 5. Investigation

**Q1 — Was this an authorised change?**
No change ticket existed for account creation on this host. In a production environment this
alone justifies escalation.

**Q2 — Who created it, and how did they get there?**
`subjectUserName` = `lab-admin`, `subjectLogonId` = `<LOGON_ID>`. Pivoting on the logon ID:

```
data.win.eventdata.logonId:"<LOGON_ID>" AND data.win.system.eventID:4624
```

returned a **logon type 3 (network) from <SOURCE_IP>** at <TIMESTAMP> — i.e. the account was
created by a **remote** session, not by someone sitting at the machine. That is the single most
important finding in this incident: the actor was already remote-capable before the account
was created.

**Q3 — What exactly ran?**
Sysmon EID 1 shows `net.exe user … /add` and `net.exe localgroup administrators … /add`, with
`cmd.exe` as the parent. Note that Windows delegates to `net1.exe`, which is why the Sysmon
config and rules cover both binaries — a rule watching only `net.exe` would show half the story.

**Q4 — Is the new account privileged?**

```powershell
Get-LocalGroupMember -Group "Administrators"
net user lab-svc-update
```

Confirmed member of **Administrators**. Not a member of Remote Desktop Users, so no RDP path
was created.

**Q5 — Has the account been used?**

```
data.win.eventdata.targetUserName:"lab-svc-update" AND data.win.system.eventID:4624
```

**No results.** The backdoor was created but not yet used — the detection caught it inside the
same minute.

**Q6 — Is there other persistence?**
Checked 4698 (tasks), 7045 (services), registry Run keys (Sysmon EID 12/13), Startup folder
(EID 11) for the 24 hours around the event. **None found.** The account was the only
persistence mechanism.

**Q7 — Were other accounts touched?**
No other 4720/4726/4732 events in the period. `Get-LocalUser` output was compared against the
baseline captured at the `03-fully-instrumented` snapshot; `lab-svc-update` was the only
difference.

## 7. Findings

1. **An unauthorised privileged local account was created and promoted within 38 seconds.**
2. **The creating session was remote (logon type 3 from <SOURCE_IP>)**, which means the actor
   already had valid administrative credentials for this host before the incident began.
   *The account creation is a symptom; the credential compromise is the root cause.*
3. **The account was never used to authenticate** — detection and containment preceded use.
4. **The naming was deliberately camouflaged** (`lab-svc-update` mimics a legitimate service
   account), which is exactly why the detection is built on the *action* rather than on
   suspicious-looking names.
5. **Correlation added real value.** `100120` alone is Medium; correlating creation with
   promotion produced a level-13 alert that could not reasonably be ignored.
6. **No other persistence existed**, so eradication was straightforward.

## 9. Recommendations

| # | Recommendation | Priority | Rationale |
|---|---|---|---|
| 1 | Treat every 4720 on a workstation as an incident until proven otherwise | High | The base rate is near zero; the cost of review is minutes |
| 2 | Investigate how `lab-admin` credentials were usable remotely — this is the real root cause | High | The account creation was the second step, not the first |
| 3 | Deploy Windows **LAPS** so local admin passwords are unique per host | High | Stops one compromised local admin password from working everywhere |
| 4 | Restrict network logon (type 3) for local administrator accounts (*Deny access to this computer from the network*) | High | Removes the exact path used here |
| 5 | Prefer `New-LocalUser` over `net user` in admin runbooks | Medium | `net user <name> <password>` puts the **plaintext password in the command line**, which is then logged by Sysmon/4688 and shipped to the SIEM |
| 6 | Add a weekly scheduled review of local accounts and Administrators membership | Medium | Catches accounts created while logging was down |
| 7 | Alert on any local account whose name matches `svc-*` being added to Administrators | Low | Service accounts should not be interactive administrators |

## 10. Lessons learned

* **Correlation beats single events.** The creation alert alone would likely have been triaged
  as routine IT activity; the 38-second link to a privileged group made the intent undeniable.
* **Always pivot on `subjectLogonId`.** It converted "an admin created an account" into "a
  *remote* session created an account", which changed the entire incident.
* **`net user` leaks passwords into telemetry.** A genuine operational finding from the lab,
  now reflected in the hardening recommendations.
* **Disable, do not delete.** Evidence preservation discipline was applied and documented.
* **Detection gap identified:** no alert exists for *account creation outside business hours*.
  Raised as SO-DET-003-B.
