# SOC L1 Investigation Workflow

The workflow every alert in this lab is worked through, from the moment it appears on the
dashboard to the moment the ticket is closed.

```
   ALERT
     |
     v
   TRIAGE            Is this worth my time right now?
     |
     v
   VALIDATE          Is the alert technically correct?
     |
     v
   INVESTIGATE       What actually happened?
     |
     v
   COLLECT EVIDENCE  What can I prove, and preserve?
     |
     v
   DETERMINE SEVERITY  How bad is it, really?
     |
     v
   CONTAIN / ESCALATE  Stop the bleeding or hand it over
     |
     v
   DOCUMENT          Write it so someone else can follow it
     |
     v
   CLOSURE           Verdict, lessons, tuning
```

---

## Stage 1 — Triage

**Goal:** decide, in under two minutes, whether this alert needs work now, later, or never.

| | |
|---|---|
| **What the analyst checks** | Severity level, rule name and description, affected host and user, source IP, timestamp, how many related alerts fired, whether this host/rule is already in an open ticket |
| **Evidence collected** | The alert itself: rule ID, level, agent name, timestamp (UTC), key fields from the description |
| **Questions asked** | What fired and why? Which asset — is it critical? Is this a one-off or part of a burst? Has this same alert already been triaged and tuned this week? Is there an obvious benign explanation (patch window, known scanner, IT change)? |
| **Escalate when** | Level 12+ on a critical asset; multiple detections firing on the same host within minutes (this is the strongest early signal of a real intrusion); any alert indicating log clearing, audit policy change or Sysmon tampering |
| **Close when** | It is an exact duplicate of an already-triaged alert, or it matches a documented, approved tuning exception (record the reference — never close silently) |

**Triage priority used in this lab**

| Priority | Criteria | Target start |
|---|---|---|
| P1 | Level 12–15, or confirmed successful attacker action | Immediately |
| P2 | Level 8–11, or several Medium alerts on one host | Within 1 hour |
| P3 | Level 4–7 | Within the shift |
| P4 | Level 0–3 | Context only, batch review |

---

## Stage 2 — Validate

**Goal:** confirm the alert is technically correct *before* spending investigation time on it.

| | |
|---|---|
| **What the analyst checks** | The raw event behind the alert (expand the JSON in *Discover*), that the rule logic matches what the event actually says, that timestamps and time zones line up, that the agent is healthy and had not been disconnected |
| **Evidence collected** | The raw event JSON, the rule ID and its condition, the decoded field values |
| **Questions asked** | Does the event really contain what the rule claims? Is this a decoding artefact? Is the source IP real or an internal loopback? Did the clock skew make this look like it happened at a different time? Was this alert generated by my own lab testing? |
| **Escalate when** | Validation confirms an unambiguous attacker action (e.g. a successful logon after a brute-force burst) |
| **Close when** | The alert is a **false positive** — the rule fired but the behaviour is legitimate. Record the cause and raise a tuning task; do not simply close |

> **Discipline point:** "false positive" means *the rule fired on legitimate activity*.
> It does not mean "I do not understand this alert". Unclear alerts get investigated, not closed.

---

## Stage 3 — Investigate

**Goal:** reconstruct what happened, in order, with evidence.

| | |
|---|---|
| **What the analyst checks** | Everything on that host ±30 minutes around the alert; the process tree; the logon session; network connections; file writes; account and group changes; other hosts showing the same pattern |
| **Evidence collected** | Process tree (image, command line, parent, user, hashes, PID/GUID), logon events (4624/4625 with type and source IP), Sysmon EID 3/11/22 for the same `ProcessGuid`, related alerts, user confirmation |
| **Questions asked** | **What** ran? **Who** ran it? **How** did it get there (the parent chain)? **When** did it start and is it still running? **Where else** has this happened? **What did it touch** — files, network, accounts, registry? **Did it succeed?** |
| **Escalate when** | Evidence of execution, persistence, privilege escalation, credential access or lateral movement — or when the investigation exceeds the L1 skill/authority boundary |
| **Close when** | The full chain is explained by legitimate activity and you can show the evidence for that conclusion |

### The four pivots an L1 must know

| Pivot | From | To | Query |
|---|---|---|---|
| **Process → session** | `logonId` in Sysmon EID 1 | The 4624 that created the session | `data.win.eventdata.logonId:"0x3e7a1"` |
| **Process → activity** | `processGuid` | Sysmon EID 3, 11, 22, 5 for the same process | `data.win.eventdata.processGuid:"{...}"` |
| **Source IP → everything** | `ipAddress` | All events involving that host | `data.win.eventdata.ipAddress:"192.168.56.30"` |
| **Account → everything** | `targetUserName` | Logons, creations, group changes | `data.win.eventdata.targetUserName:"lab-svc-update"` |

### Standard investigation queries (Wazuh Discover)

```
agent.name:"WIN-SOC-EP01" AND rule.level:>=8
data.win.system.eventID:(4625 OR 4624 OR 4720 OR 4732 OR 4688 OR 4104)
data.win.eventdata.parentImage:*winword.exe
data.win.eventdata.image:*\\Temp\\*
rule.mitre.id:"T1059.001"
rule.groups:"authentication_failed" AND data.win.eventdata.ipAddress:"192.168.56.30"
```

### Live host triage commands (MANUAL STEP, run on the endpoint)

```powershell
Get-LocalUser | Select-Object Name, Enabled, LastLogon, PasswordLastSet
Get-LocalGroupMember -Group "Administrators"
Get-Process | Select-Object Id, ProcessName, Path, StartTime | Sort-Object StartTime -Descending
Get-NetTCPConnection -State Established | Select-Object LocalPort, RemoteAddress, RemotePort, OwningProcess
Get-ScheduledTask | Where-Object State -ne 'Disabled' | Select-Object TaskName, TaskPath, Author
Get-CimInstance Win32_Service | Where-Object PathName -notlike 'C:\Windows\*' | Select-Object Name, PathName, StartName
Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Run"
Get-FileHash C:\Users\Public\suspect.exe -Algorithm SHA256
```

## Stage 4 — Collect evidence

**Goal:** make the findings provable and preserved, even if the host is later rebuilt.

| | |
|---|---|
| **What the analyst checks** | That every claim in the report is backed by a specific artefact with a timestamp |
| **Evidence collected** | Alert IDs and rule IDs; raw event JSON exports; screenshots of the dashboard with the time range visible; file hashes (SHA256); IOC list (IPs, domains, URLs, filenames, account names, task/service names); exported `.evtx` where required |
| **Questions asked** | Can I reproduce this finding from the saved evidence alone? Is anything here sensitive and needing redaction before it leaves the SOC? Have I recorded the time zone? |
| **Escalate when** | Evidence must be preserved for legal/HR purposes — stop and involve IR/management before touching the host further |
| **Close when** | Never closed at this stage — evidence collection supports the next stages |

**Evidence handling rules used in this lab**

1. Record **UTC** timestamps everywhere.
2. Never alter the source host before evidence is captured — **disable** accounts, do not delete
   them; **isolate** hosts, do not reimage them.
3. Hash anything you collect; note the hash in the report.
4. Redact before publishing: real usernames, real internal IPs, hostnames, licence keys.
5. Note the collection method and who collected it.

```powershell
# Export the relevant window for offline preservation (MANUAL STEP)
wevtutil epl Security C:\Lab\Evidence\SEC_20260901.evtx `
  "/q:*[System[TimeCreated[@SystemTime>='2026-09-01T10:00:00.000Z' and @SystemTime<='2026-09-01T12:00:00.000Z']]]"
Get-FileHash C:\Lab\Evidence\SEC_20260901.evtx -Algorithm SHA256
```

## Stage 5 — Determine severity

**Goal:** assign a severity you can defend, based on evidence rather than on the rule's level.

The rule's level is a **starting point**. Final severity is a function of impact and confidence:

| | Attacker action **not** successful | Attacker action successful |
|---|---|---|
| **Non-critical asset** | Low | Medium |
| **Standard workstation** | Low–Medium | High |
| **Privileged account involved** | Medium | **Critical** |
| **Multiple hosts affected** | High | **Critical** |

Questions that move severity:

* Did it succeed? (failed brute force vs. successful logon)
* What privileges were involved? (standard user vs. Administrators vs. SYSTEM)
* Is there persistence? (a new account, task or service means it survives a reboot)
* Is data involved? (staging, archiving or exfiltration evidence)
* How many hosts? (one is an incident; several is a campaign)
* Is it still happening? (active > historical)

## Stage 6 — Containment / escalation

**Goal:** stop the damage, or hand over cleanly to someone who can.

| | |
|---|---|
| **What the analyst checks** | Whether the activity is ongoing; what the L1 mandate actually permits; who the asset owner is |
| **Evidence collected** | Timestamp of every containment action taken, and by whom |
| **Questions asked** | Will containment destroy evidence? Will it tip off the attacker? What is the business impact of isolating this host? Am I authorised to do this? |
| **Escalate when** | Any confirmed compromise; anything requiring host isolation, account disablement or a password reset beyond your mandate; anything touching more than one host; anything involving privileged accounts or data loss |

**Typical L1 containment actions (within mandate, in this lab)**

| Action | Command | Caution |
|---|---|---|
| Disable a compromised account | `Disable-LocalUser -Name "lab-svc-update"` | Disable, never delete — preserve the SID |
| Block a source IP at the host | `New-NetFirewallRule -DisplayName "IR block" -Direction Inbound -RemoteAddress 192.168.56.30 -Action Block` | Document the rule so it can be removed later |
| Kill a malicious process | `Stop-Process -Id <pid> -Force` | Capture the process details **first** |
| Remove a backdoor scheduled task | `Unregister-ScheduledTask -TaskName "..." -Confirm:$false` | Export the task XML first |
| Isolate the host | Detach the virtual NIC / apply the EDR isolation policy | Coordinate with the asset owner |

**Escalation handover must contain:** what fired, what you verified, the timeline, the evidence
locations, the IOCs, the actions you already took, and your open questions. An escalation
without a timeline forces the next analyst to start over.

## Stage 7 — Documentation

**Goal:** write the incident so a colleague — or you in six months — can follow it without
asking questions.

Every incident in [`/incidents`](../incidents) uses the same structure: Incident ID, date/time,
alert name, severity, affected host, user, source IP, detection source, description, timeline,
indicators, investigation, MITRE mapping, findings, response, recommendations, final status.

| Write this | Not this |
|---|---|
| "12 failed logons for `svc-backup` from 192.168.56.30 between 09:14:02 and 09:14:35 UTC, all sub-status 0xC000006A (wrong password). No 4624 for that account from that IP in the following 24 h." | "User had login issues, looks like brute force, probably fine." |
| "No evidence of successful authentication was found in the Security log for the period reviewed." | "Nothing happened." |
| "Root cause could not be determined from available telemetry because network logs are not collected in this lab." | *(silence)* |

State what you **did not** check, and why. Unstated gaps are how incidents get closed twice.

---

## Stage 8 — Closure

**Goal:** end the ticket in a state that improves the SOC.

| | |
|---|---|
| **What the analyst checks** | Verdict is explicit; all evidence is attached; response actions are recorded with timestamps; follow-up tasks have owners |
| **Questions asked** | Is the threat actually gone? Does a rule need tuning? Was a detection missing (a false negative)? Does a playbook need updating? Should anything here become a hardening recommendation? |
| **Close when** | True positive: threat contained/remediated and verified. False positive: cause identified and tuning task raised. Benign: explanation documented with evidence |

**Closure categories used**

| Category | Meaning |
|---|---|
| True Positive — Contained | Real malicious activity, stopped |
| True Positive — Benign Simulation | Real detection, activity was authorised lab testing (**used for most incidents in this repository**) |
| False Positive | Rule fired on legitimate activity — tuning required |
| Inconclusive | Insufficient telemetry — state the gap and what would have been needed |
| Duplicate | Already covered by another ticket (reference it) |

**Every closed alert should leave one of three things behind:** a tuned rule, a new detection,
or a hardening recommendation. If it leaves nothing, the time spent was wasted.
